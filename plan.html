0프로젝트 진행 방식

우리 팀은 데이터를 직접 만들지 않습니다. 요청서를 보내면 다른 팀이 오염이 섞인 가상 로그를 만들어 주고, 우리는 그 데이터를 받아 3일 안에 결과물을 완성합니다. 데이터 팀은 정답지(어떤 계정이 봇인지, 어디에 오염을 넣었는지)를 따로 보관하고, 우리 결과를 채점하는 데 씁니다.

1무엇을 만드는가

MMORPG "○○온라인"의 유저 로그를 정제하고, 매크로 봇 · 작업장 · 현금 거래(RMT) 계정을 찾아내는 데이터 파이프라인과 운영 대시보드입니다.

정제 없이는 탐지도 없다

중복 이벤트 하나 때문에 정상 유저가 "초당 사냥 10회"로 집계돼 봇으로 오탐됩니다. 엔씨소프트도 대회 데이터를 낼 때마다 오류가 발견돼 다시 추출했습니다(별첨 B-11). 이 프로젝트는 정제 전후로 탐지 결과가 어떻게 달라지는지를 숫자로 보여 줍니다.

최종 산출물 5가지

01

메달리온 파이프라인

받은 파일을 Bronze → Silver → Gold로 적재·정제하는 코드. 명령 한 줄로 처음부터 다시 돌릴 수 있어야 합니다.

02

데이터 품질 리포트

오염 유형별로 몇 건을 찾았고 어떻게 처리했는지 정리한 리포트. 데이터 팀 정답지와 비교한 탐지율도 포함합니다.

03

봇 · 작업장 탐지 결과

계정별 위험 점수와 탐지 사유. 정답지 대비 정밀도와 재현율, 정제 전후 오탐률 비교.

04

운영 대시보드

Streamlit 웹 대시보드 5개 화면: 현황, 데이터 품질, 의심 계정, 계정 타임라인, 거래 네트워크.

05

발표 자료 · README

문제 정의, 구조, 결과 수치, 시연. GitHub 저장소 README에 실행 방법과 데이터 출처를 적습니다.

3탐지 로직

필수 · 규칙

명확한 신호

  • 매크로: 행동 간격 편차가 아주 작음, 하루 20시간 이상 접속, 같은 좌표 반복
  • 작업장: 같은 IP · 기기의 여러 계정, 비슷한 시각에 만든 계정의 같은 동선
  • RMT: 여러 계정의 골드가 한 계정으로 집중, 시세와 동떨어진 거래
필수 · 그래프

관계로 찾기

  • 거래를 계정 간 네트워크로 구성
  • 골드가 모이는 허브 계정 탐지
  • IP · 기기로 묶이는 계정 군집
선택 · ML

시간이 남으면

  • Isolation Forest로 이상치 점수
  • 정답지로 규칙 기반과 성능 비교
  • 헤비 유저 오탐이 줄어드는지 확인

핵심 특징값 예시: 행동 간격

예시 그림 · 사람은 행동 간격이 불규칙하지만 매크로는 거의 일정합니다. 다만 오래 플레이하는 헤비 유저는 봇과 헷갈리기 쉬워서, 실제 연구에서도 헤비 유저를 따로 나누자 오탐이 881건에서 327건으로 줄었습니다(별첨 B-4).

5기술 스택

3일 안에 끝내야 하므로 서버를 띄우지 않고 노트북 한 대에서 도는 구성을 기본으로 합니다. Kafka와 Airflow는 시간이 남을 때만 붙이는 확장 항목입니다.

영역도구고른 이유구분
언어 · 환경Python 3.11, uv(또는 venv + requirements.txt)세 명이 같은 환경을 몇 분 안에 맞출 수 있음필수
저장 · 처리DuckDB, Parquet설치 없이 파일 하나로 쓰는 분석용 DB. 수천만 행도 노트북에서 SQL로 빠르게 처리필수
데이터 가공Polars (또는 pandas)대용량에서 pandas보다 빠르고 메모리를 적게 씀필수
품질 검사SQL 규칙 파일 + pytest규칙을 파일로 관리하고 자동 실행. 별첨 B-11의 "데이터에도 단위 테스트" 교훈을 그대로 적용필수
네트워크 분석NetworkX거래 그래프의 허브 · 군집 계산필수
대시보드Streamlit, Plotly, pyvis파이썬만으로 웹 대시보드를 하루 안에 만들 수 있음필수
협업GitHub (저장소 · Projects 칸반 · PR), Discord작업 현황과 코드 리뷰를 한곳에서필수

6업무 방식

매일 오전 10분 스탠드업(어제 한 일 · 오늘 할 일 · 막힌 것), 오후 늦게 15분 통합 점검. Discord 음성 채널을 작업 시간 내내 열어 둡니다.

작업 관리

GitHub Projects 칸반(할 일 → 진행 중 → 리뷰 → 완료). 카드 하나는 반나절 안에 끝나는 크기로 쪼갭니다.

브랜치 · 리뷰

main은 항상 실행되는 상태로 유지. 기능별 브랜치 → PR → 다른 한 명이 확인 후 병합. 커밋 메시지는 feat: · fix: · docs: 형식으로 씁니다.

완료 기준

코드가 make all에 연결돼 있고, 품질 검사를 통과하고, README에 한 줄 이상 설명이 있으면 "완료"입니다.

데이터 계약

2차 요청서의 스키마가 곧 계약입니다. 받은 데이터가 스키마와 다르면 우리 코드를 고치기 전에 데이터 팀에 먼저 묻습니다. 질문과 답은 공유 문서에 기록합니다.

막히면 30분 규칙

30분 넘게 막히면 바로 공유합니다. 3일 프로젝트에서는 혼자 고민하는 시간이 가장 비쌉니다.

9범위와 위험

필수 (MVP)

Bronze → Silver → Gold, 오염 9종 처리와 품질 리포트, 규칙 · 네트워크 탐지, 정답지 채점, 대시보드 5화면, 발표 자료.

확장 (여유 시)

Isolation Forest 비교, Kafka 실시간 재생 시연, Airflow DAG, Streamlit Cloud 배포, 실제 데이터(별첨 A)로 교차 검증.

위험대응
데이터가 늦게 온다0일차에 샘플(1일치)을 먼저 받아 뼈대를 완성해 둡니다. 본 데이터는 같은 스키마라 바로 갈아 끼웁니다.
데이터가 스키마와 다르다Bronze에서 스키마 검사를 먼저 돌려 차이를 목록으로 만들고, 데이터 팀에 즉시 공유합니다. 차이 자체도 "오염"으로 리포트에 넣습니다.
데이터가 너무 크다Parquet + DuckDB로 처리하고, 개발은 하루치로 하고 전체는 마지막에 한 번 돌립니다.
탐지 성능이 낮다성능보다 "정제 전후 차이"와 "왜 이 규칙인가"를 설명하는 데 집중합니다. 출제자들도 점수보다 설명을 더 중요하게 봤습니다(별첨 B-11).
시연 중 오류3일차 오후에 시연 영상을 미리 녹화해 둡니다.

"왜 처음부터 ML을 쓰지 않았나요?"
