B-1데이터셋 · 대회

Game Bot Detection Challenge (정보보호 R&D 데이터 챌린지 2019 게임봇 탐지 트랙)

제공
고려대학교 해킹대응기술연구실(HCRL) · 원천 데이터: 엔씨소프트 아이온
원문
ocslab.hksecurity.net/Datasets/datachallenge2019/gamebot
언어
영어 → 번역
배경
  • 이 데이터는 "정보보호 R&D 데이터 챌린지 2019"의 게임봇 탐지 트랙에서 쓰였습니다.
  • 유저 활동 로그로 구성되며, 예선과 본선에는 서로 다르지만 이어지는 기간의 로그를 썼습니다.
게임
  • 아이온(AION): 엔씨소프트가 2008년 11월부터 서비스한 MMORPG입니다.
데이터 구성
  • 전체 크기 184GB, 기간은 2010-04-16부터 2010-05-07까지 22일입니다.
  • 페이지에 소개된 필드: actor·target(캐릭터 ID 또는 NPC ID), actor_account·target_account(계정 ID 또는 NPC ID). 나머지 필드나 파일 목록은 페이지에 없습니다.
익명화
  • 개인 식별 정보가 담길 수 있는 캐릭터 이름 같은 민감 정보는 삭제했습니다.
  • IP 주소, 캐릭터 ID, 계정 ID는 실제 유저 보호를 위해 무작위 값으로 바꿨습니다.
  • 예선과 본선 데이터를 함께 변환했기 때문에, 두 기간에 모두 활동한 캐릭터는 같은 ID를 가집니다. 대회 당시 제공된 데이터와는 이 점이 다릅니다.
라벨링
  • 유효한 계정 목록에 정상(0) 또는 게임봇(1) 라벨이 붙어 있습니다.
  • 로그 기간 동안 3시간 넘게 활동한 캐릭터가 하나 이상 있는 계정만 포함했습니다.
  • 정답은 게임사가 제공한 제재 목록입니다. 제재된 유저는 모두 사람의 검토와 모니터링으로 검증했습니다.
받는 방법
  • 김휘강 교수(cenda@korea.ac.kr)에게 신분과 사용 목적을 적어 메일을 보내면 됩니다.
인용을 요청한 논문
  • Kang 외 (2016). Multimodal game bot detection using user behavioral characteristics. SpringerPlus, 5(1).
  • Kwon 외 (2016). Crime scene reconstruction: Online gold farming network analysis. IEEE TIFS, 12(3).
  • Lee 외 (2016). You are a Game Bot!: Uncovering Game Bots in MMORPGs via Self-similarity in the Wild. NDSS.
페이지에 없는 정보
  • 계정·캐릭터·레코드·봇 수, 클래스 비율, 라이선스와 재배포 조건은 적혀 있지 않습니다.
우리 프로젝트에 주는 시사점 · 정답이 "실제 제재 기록"이라 탐지 로직을 검증하기에 가장 신뢰할 만한 데이터입니다. "3시간 이상 활동 계정만 포함" 같은 필터 기준도 우리 Gold 레이어에 그대로 가져올 수 있습니다.

Game Bot Detection Dataset Based on User Behavioral Characteristics

저자
강아름, 정성훈(고려대), Aziz Mohaisen, 김휘강(고려대)
등록
IEEE DataPort, 2025-11-24 · DOI 10.21227/8q6x-bp56
원문
ieee-dataport.org/documents/game-bot-detection-dataset-…
언어
영어 → 번역
설명
  • 대형 MMORPG 서비스의 장기간 게임 내 행동 로그입니다. 게임 이름은 적혀 있지 않습니다.
  • 88일간의 플레이, 캐릭터 49,739명, 그중 운영사가 봇으로 확인한 캐릭터 7,702명을 담고 있습니다.
  • 사냥, 채집, 거래, 채팅, 파티 같은 활동의 서버 이벤트 로그에서 특징값을 뽑았습니다. 개인정보는 게임사 내부 정책에 따라 익명화했습니다.
포함된 특징값 (페이지의 "일반적으로 포함" 목록)
  • 플레이어 정보: 로그인 빈도, 플레이 시간, 게임 머니, 고유 IP 수
  • 플레이어 행동: 앉기, 경험치 획득, 아이템 획득, 돈 획득, 채집(최대 횟수 포함), PK 포인트, 부활, 포털 사용 횟수. 반복적이고 좁은 플레이를 잡아내기 위해 행동 비율도 포함합니다.
  • 그룹 활동: 파티 플레이 시간, 길드 활동 횟수
  • 소셜 상호작용 다양성: 파티, 친구, 거래, 귓속말, 우편, 상점, 길드 상호작용의 섀넌 엔트로피
  • 네트워크 지표: 6개 방향성 네트워크(파티, 친구, 거래, 귓속말, 우편, 상점)에 대한 중심성(연결·매개·근접·고유벡터), 이심률, 허브·권위 점수, 페이지랭크, 군집 계수. 네트워크 모티프와 트라이어드 센서스도 쓸 수 있다고 합니다.
라벨 · 파일 · 이용
  • 0 = 사람, 1 = 게임봇 (운영사가 확인한 제재 계정 목록 기준)
  • "Game Bot Detection.zip" 514.57MB, CSV와 TXT 형식. 행 수는 적혀 있지 않습니다.
  • 로그인과 구독이 필요합니다. 라이선스는 적혀 있지 않습니다. 관련 논문은 SpringerPlus(2016)입니다.
우리 프로젝트에 주는 시사점 · 봇 비율(약 15.5%)과 특징값 목록을 생성기와 탐지 규칙 설계에 그대로 참고할 수 있습니다. 특히 "소셜 다양성(엔트로피)"은 봇이 사회 활동을 거의 하지 않는다는 점을 숫자로 잡아내는 좋은 특징값입니다.

원문

언어

우리 프로젝트에 주는 시사점 · 2단계 그래프 분석의 근거 자료입니다. "봇 사용은 친구를 통해 전염된다"는 관점으로 작업장 네트워크를 설명할 수 있습니다.
B-4논문

Understand Watchdogs: Discover How Game Bot Get Discovered

저자
박은지, 박경호, 김휘강 (고려대 정보보호학부)
원문
arXiv 2011.13374
언어
영어 → 번역
초록
  • 게임봇은 다른 플레이어를 방해하고 게임 경제를 망가뜨립니다. 게임사는 학습 기반 탐지기를 쓰지만, 탐지기는 판단 이유를 거의 설명하지 못합니다.
  • 저자들은 아이온의 사람·봇 로그로 설명 가능한 AI(XAI) 모델을 만들고, 설명이 얼마나 믿을 만한지 평가했습니다. 해석 가능성이 사람을 봇으로 잘못 제재하는 일을 줄일 수 있다고 주장합니다.
1. 서론
  • 게임봇은 게임 자산을 자동으로 모으는 프로그램입니다. 게임 자산을 현금으로 파는 현금 거래(RMT)에 쓰기 좋고, 약한 몬스터 사냥 같은 행동을 반복합니다.
  • 작업장(Gold Farmer Group)은 봇을 대량으로 운영해 불법 수익을 냅니다. 싼값에 자산을 팔아 게임사의 인앱 결제를 잠식하고, 아이템을 독점하고, 일반 유저를 떠나게 합니다.
  • 초기 탐지는 채팅, 소셜 이벤트 등에서 봇 패턴을 찾는 데이터 마이닝이었습니다. 특징값 설계에 크게 의존해서, 봇이 행동을 바꾸거나 게임이 업데이트되면 무너졌습니다.
  • 머신러닝과 딥러닝은 성능이 좋지만 개별 판정의 이유를 설명하지 못합니다. 운영자는 봇 판정의 근거가 필요합니다.
2. 선행 연구 (탐지 방법 분류)
연구데이터방법 · 핵심
Kang 외 2013아이온규칙 기반. 봇은 2인 파티를 맺고, 평균보다 오래 접속하며, 경험치 로그가 많고 종족 포인트 로그가 적음. 정확도 95.92%
Chung 외 2013열혈강호 온라인행동 특징 12개 + 고급 특징 5개, 플레이 스타일 4유형으로 군집화 후 다중 SVM
Lee 외 2016리니지, 아이온, 블소봇의 "자기 유사성"(같은 행동 반복) 활용, 로지스틱 회귀 정확도 95%
Lee 외 2018리니지캐릭터 간 거래를 네트워크로 그려 암시장 노출
Park 외 2019아이온재화 시계열 LSTM, 정확도 95% 이상
Tsaur 외 2019KANO딥러닝으로 이상 비율 계산, 봇처럼 행동하는 "회색 지대" 유저 제시
Tao 외 2018 (NGUARD)NetEase MMORPG전처리·온라인 추론·자동 반복·오프라인 학습 프레임워크, ABLSTM, 정밀도 97% 이상
3. 실험
  • 데이터: 엔씨소프트 아이온 로그를 고려대 HCRL이 전처리. 3시간 넘게 플레이한 49,530명(봇 6,213명), 4월 10일 ~ 7월 5일 88일. 라벨은 엔씨소프트의 수동 로그 검토로 확인했고, 고객 문의로 혐의를 벗은 경우 라벨을 고쳤습니다. 클래스 불균형은 오버샘플링과 언더샘플링으로 처리했습니다.
  • 특징값 40개 (3분류): 플레이어 정보(로그인·로그아웃 횟수, 플레이 시간, 돈, 총 로그인 수, IP 수, 최고 레벨), 플레이어 행동(채집, 앉기, 경험치, 아이템, 돈, 어비스, 경험치 복구, 포털, 사망, 텔레포트, 부활), 소셜 활동(파티 시간, 길드 활동, 길드 가입, 소셜 다양성). 레벨 5 미만 플레이어는 제외했습니다.
  • 모델: 랜덤 포레스트(검증 정확도 88.51%), 다층 퍼셉트론(90.10% 이상). 설명 기법은 특징 중요도, 순열 중요도, LIME(SP-LIME), SHAP.
4. 결과
  • 랜덤 포레스트 특징 중요도 1위는 하루 플레이 시간, 그다음이 하루 아이템 획득 횟수와 경험치 획득 횟수였습니다.
  • LIME 사례 분석: 봇은 사람보다 하루 경험치 획득량이 압도적으로 많았습니다.
  • SHAP: 플레이 시간의 영향이 가장 컸고, 로그인 횟수와 경험치 획득 횟수가 뒤를 이었습니다.
  • 상위 특징을 빼도 정확도는 거의 떨어지지 않았습니다(88.21~89.37%).
  • 헤비 유저 분석: 오탐 사례에서 경험치 획득 비율이 가장 큰 영향을 줬습니다. "사람"에서 "헤비 유저"를 별도 클래스로 떼어 내자 정확도가 96.02%로 오르고 오탐이 881건에서 327건으로 줄었습니다.
5. 결론
  • LIME이 가장 좋은 설명을 줬다고 평가했습니다. 헤비 유저와 봇은 둘 다 자산을 빨리 모아 과거 모델을 헷갈리게 했는데, XAI가 이를 풀었다고 주장합니다. 설명은 억울한 제재에 대한 이의 제기와 로그 설계 개선에도 도움이 됩니다.
우리 프로젝트에 주는 시사점 · ① 생성기에 "헤비 유저"를 꼭 넣어야 오탐 문제를 시연할 수 있습니다. ② 대시보드의 "탐지 사유" 칸에 SHAP·LIME 설명을 붙이면 운영자 관점의 완성도가 올라갑니다.

초록 · 동기
  • 게임사는 데이터를 거의 공유하지 않아서 게임 데이터 마이닝과 AI 연구가 제한됩니다. 저자들은 엔씨소프트 블레이드 앤 소울의 1만 명, 약 100GB 로그로 국제 대회를 열고 데이터를 공개했습니다.
  • 과제는 월정액에서 부분 유료화로 바뀌는 시기를 넘어 유저의 이탈 여부와 시점을 예측하는 것이었습니다. 상위권은 딥러닝, 트리 부스팅, 선형 회귀를 썼습니다.
  • 기존 게임 AI 대회는 게임을 플레이하는 에이전트 위주였고, 게임 로그 연구는 2013년 급증 이후 정체됐다고 봅니다.
대회 설계
  • 대상: 누적 결제가 기준 이상이고 활동이 많은 충성 유저만 포함했습니다. 가벼운 유저와 악성 유저는 제외했습니다. 엔씨소프트는 결제·플레이 시간·콘텐츠 이용으로 k-means를 돌려 유저를 14개 충성도 등급(낮을수록 충성)으로 나누는데, 최근 3개월 중 9등급 이상을 두 번 이상 받은 유저(전체의 30% 미만)를 골랐습니다.
  • 이탈 정의: 5주 넘게 플레이하지 않은 유저. 서버 점검에 맞춰 주는 수요일~수요일로 셉니다.
  • 예측 시점: 5주 이탈 창이 시작되기 3주 전에 예측합니다.
  • 생존 분석(트랙 2): 관측이 끝나지 않은 유저가 있어서 오른쪽 중도절단(right-censored) 문제로 다룹니다.
  • 개념 변화: 테스트 1은 학습 데이터 2개월 뒤, 테스트 2는 7개월 뒤 데이터입니다. 그 사이 2016년 12월에 사업 모델이 바뀌었습니다. 라벨 없는 테스트 데이터를 학습에 써도 됐습니다.
데이터
  • 로그 유형은 수백 가지지만 대회에는 주요 82가지(접속, 캐릭터, 아이템, 스킬, 퀘스트, 길드)를 썼습니다.
  • 로그 유형마다 77개 필드가 있고 4개 그룹으로 나뉩니다: 공통(로그 유형, 시각, 위치), 행위자(ID, 레벨, 종족), 대상물(아이템 ID, 등급, 수량, 스킬명), 대상(대상 ID, 골드, 받은 피해).
  • 악성 활동 정황이 있는 유저는 제거했습니다. 엔씨소프트의 탐지 규칙은 기밀입니다.
평가 · 일정 · 참가
  • 트랙 1은 F1 점수, 트랙 2는 RMSLE(낮을수록 좋음). 중도절단 때문에 실제보다 길게 예측하면 맞힌 것으로 처리했습니다.
  • 2017.4.15 샘플과 스키마 공개 → 4.30 전체 데이터 공개 → 5.19 테스트 서버(테스트 데이터 10%) → 마감 7.31에서 8.10으로 연장.
  • 구글 그룹 가입자는 약 300명. 한국, 독일, 핀란드, 일본에서 제출했고, 트랙 1은 13팀, 트랙 2는 5팀이 제출했습니다.
결과
  • 트랙 1: Yokozuna Data 1위(최종 약 0.62, 테스트 1 0.61, 테스트 2 0.63). UTU, TripleS, TheCowKing이 0.60. 기준선(특징 22개 + 라쏘 회귀)은 F1 0.48이었고, 13팀 중 8팀이 기준선을 넘었습니다.
  • 트랙 2: Yokozuna Data 1위(0.72). IISLABSKKU 0.81, UTU 0.91, TripleS 0.92, DTND 0.97. 테스트 서버 최고 점수는 0.41이었지만 최종과는 차이가 컸습니다.
  • 테스트 서버(10% 데이터)와 최종 순위가 크게 달랐습니다. 저자들은 과적합 때문으로 봅니다.
  • 참고할 만한 접근: MNDS는 8주 시계열을 13×56 픽셀 이미지(Gramian Angular Field)로 바꿔 Inception-V3에 넣었습니다. goedle.io는 약 600개 이벤트 기반 특징값을 만들고 이상치 유저 0.5%를 제거했습니다.
교훈
  • 트랙 1에서 압도적인 기법은 없었습니다. 학습 알고리즘보다 특징 설계, 전처리, 선택이 더 중요했습니다.
  • 충성 유저만으로 학습하면 F1이 0.39~0.53으로, 전체 유저(0.6~0.72)보다 훨씬 어려웠습니다.
  • 시간 간격의 영향: 같은 시기 유저에서 F1 약 0.45였던 모델이 2개월 뒤 유저에서는 0.04~0.3으로 떨어졌습니다.
  • 테스트 서버에서 정답이 새지 않도록 보안이 필요하고, 다음에는 Kaggle 같은 플랫폼을 고려해야 한다고 했습니다.
데이터 공개
  • 대회 뒤 엔씨소프트는 참가자와 다른 사람들이 교육, 학술, 연구 목적으로 데이터를 복사하고 보관하도록 허락했습니다. 테스트 라벨도 공개했습니다. 데이터는 GDMC 2017 홈페이지와 구글 그룹 페이지에서 받을 수 있다고 적혀 있습니다.

개요
  • 엔씨소프트는 2017년부터 매년 외부 분석가 대상 대회를 열었고, 2019년에는 한국정보화진흥원·빅데이터포럼 주최 빅콘테스트에 공동 주관사로 참여했습니다. 주제는 "기대 이익을 고려한 고객 이탈 예측"입니다.
  • 일정: 7월 17일 설명회 → 9월 10일까지 약 2개월 진행 → 1차 서류, 2차 본선 발표 → 11월 26일 시상식.
출제 의도
  • 시간 변화에 강한 모델: 게임은 업데이트, 밸런스 변경, 프로모션으로 행동 패턴이 자주 바뀝니다. 학습과 평가 데이터의 기간을 다르게 하고, 시기가 다른 평가 데이터를 2세트 준비했습니다.
  • 기대 이익 평가: 기대 이익 = 전환율 × (추가 생존 기간 × 일별 평균 결제 금액) − 인센티브. RMSE, AUC 같은 지표는 알고리즘의 일반 성능을 보기에는 좋지만, 구체적인 목표가 있는 예측을 평가하기에는 부적절하다는 입장입니다. 한 참가자가 "모두 이탈로 예측하면 점수가 더 높다"고 지적했는데, 출제팀은 이를 모델 자체의 문제로 봤습니다.
  • 재현성: 2018년에는 문서는 좋았지만 코드가 정리되지 않아 대부분 재현이 어려웠습니다. 분석 결과물은 "문서"가 아니라 "제품이나 서비스"가 되어야 하므로, 2019년에는 제출 형식을 엄격히 정하고 재현 여부를 심사에 반영했습니다.
참가와 심사
  • 531팀 참가(2018년과 같음), 최종 제출 38팀(2018년 93팀에서 크게 감소). 문제가 어려워지고 제출 조건이 까다로워졌기 때문으로 봅니다.
  • 1차: 예측 성능 + 재현성 + 발표 문서로 16팀 선정. 2차: 16팀 발표와 질의응답.
  • 상위권은 학습 시기에 가까운 테스트 1에서, 하위권은 오히려 테스트 2에서 성능이 높았습니다.
  • 재현성은 25점 만점에서 감점하는 방식이었고, 사전 안내 덕분에 대부분 사소한 수정만으로 재현됐습니다.
우수 접근법
  • 여전히 XGBoost, GBM, 랜덤 포레스트가 가장 많았고 딥러닝이 늘었습니다. 대상 팀 "규복동"은 생존 기간과 결제 금액을 한 딥러닝 모델로 동시에 예측하고, 손실 함수를 기대 이익 최대화로 설계해 예측 성능 최고점을 받았습니다.
  • "라이온킹" 팀은 생존 기간은 과소, 결제 금액은 과대 추정하는 게 유리하다고 보고 분위 회귀로 구현했습니다.
  • 시간 강건성 시도: 직전 대비 변화율 파생 변수, 결제 금액이 안정적인 날짜만 학습, 주식 추세 지표(MACD, RSI 등) 적용 등. 개념 변화(concept drift)에 정면으로 대응한 팀은 드물었고, 출제팀도 여러 시차의 학습 데이터를 주지 않은 설계 한계를 인정했습니다.
출제자의 교훈
  • 성능 경쟁의 한계: 1~2% 차이가 순위를 바꾸지만 실서비스에서는 크게 중요하지 않습니다. 모델 수십 개를 조합한 팀보다 PC에서 15분이면 학습되는 가벼운 모델이 실전에 더 유용해 보였습니다. 100개 넘는 모델을 조합하고도 서비스에 적용하지 못한 넷플릭스 프라이즈 사례도 언급합니다.
  • 데이터 오류: 2017, 2018년에도 공개 후 중요한 오류가 발견돼 다시 추출했고, 이번에도 오류를 수정했습니다. 데이터 종류가 많고 전처리가 복잡해 오류를 찾기 어렵다며, 데이터 분석에도 단위 테스트나 정적 분석 같은 소프트웨어 공학 기법이 필요하다고 했습니다.
  • 발표: 많은 팀이 기법 선택 이유를 "가장 성능이 좋았다"로만 설명해 본선에서 가장 많이 지적받았습니다. 스토리텔링에만 기대는 분석도 경계했습니다.
  • 대회 운영에 약 8개월간 1~2명이 매달려야 해서 부담이 커서, 2020년에는 대회를 열지 않기로 했습니다.
우리 프로젝트에 주는 시사점 · 대형 게임사도 매번 데이터 오류로 다시 추출했다는 사실은 "정제 없이는 탐지도 없다"는 우리 주장의 가장 강력한 근거입니다. 재현성(Docker, 코드 정리)과 "왜 이 기법인가"를 설명하는 것도 처음부터 준비해야 합니다.

언어

  • 빅콘테스트는 공공 데이터와 기업 실데이터를 제공하는 국내 최대 데이터 분석 대회로 7회째입니다. 매년 700여 팀, 2018년 1,100여 팀이 참가했고, 2019년 총상금은 역대 최고인 6,500만 원입니다.
  • 2019년 7월 17일 신한카드 본사 강당 문제 설명회에 약 500명이 참석했습니다.
  • 문제: 리니지 28일간의 활동 데이터로 ① 앞으로의 생존 기간, ② 그때까지의 일별 평균 결제 금액을 예측합니다.
  • 종속 변수: survival_time(1~64일, 64는 잔존), amount_spent(일별 평균 결제 금액, 음수 불가)
  • 독립 변수(테이블): 기본 활동(캐릭터별 일별 플레이 시간, 경험치, 사망·부활 횟수 등), 거래(캐릭터 간 교환, 개인 상점), 전투(일별 PvP), 혈맹(소속 혈맹원의 전투 집계), 결제(지난 28일 일별 결제 금액)
  • 대상은 약 8만 명이고, 개인 식별 정보는 마스킹·변환했습니다. 특정 유저군만 뽑지 않아 편향을 줄였습니다.
  • 자체 평가는 평가 데이터의 20%만 쓰므로 과적합에 유의해야 하고, 자체 평가 점수는 심사에 반영되지 않습니다. 재현성 평가는 작년보다 강화됩니다.
  • 팁: 이탈 여부(64 미만)와 과금 여부(0 초과)로 먼저 분류한 뒤 값을 예측하는 방법도 가능합니다. 데이터가 커서 중간 결과를 저장하며 작업하는 게 좋습니다.
우리 프로젝트에 주는 시사점 · 활동, 거래, 전투, 혈맹, 결제 5개 테이블 구조는 Gold 레이어 집계 테이블 설계의 좋은 기준입니다. 결제 데이터는 우리 범위 밖이지만, 거래와 혈맹 테이블은 작업장 탐지에 그대로 쓰입니다.
B-13출제자 후기

2018 빅콘테스트 후기

작성
엔씨소프트 DANBI, 2019-02-19
원문
danbi-ncsoft.github.io
언어
한국어 → 정리
출제 배경
  • 2017년 IEEE CIG에서 처음 대회를 열었지만 경험과 홍보가 부족해 참가 규모가 작았습니다.
  • Kaggle에 문의하니 호스팅·컨설팅 최소 6만 달러, 총상금 최소 2만 달러가 필요해 포기하고 빅콘테스트에 주관사로 참여했습니다.
  • 목적은 게임 데이터의 가치 홍보, 분석 인재 채용, 학계의 게임 데이터 연구 촉진입니다.
문제와 데이터
  • 블레이드 앤 소울 유저의 지난 8주 활동으로 향후 12주 안의 이탈 시점을 4개 라벨로 예측합니다: Week(1주 이내), 1Month(2~4주), 2Month(4~7주), Retained(8주 이상 잔존).
  • 군 입대, 시험 준비처럼 게임 밖 이유의 이탈은 데이터로 알 수 없다는 한계도 밝혔습니다.
  • 게임 활동: 주 단위 집계(계정당 최대 8행), 34개 필드. 접속 일수, 플레이 시간, NPC 사냥·퀘스트·아이템 경험치, 전투 시간, 재화 획득, 결투·전장 참여와 승리, 인던·레이드 입장과 완료, 채널별 채팅 횟수, 버프 아이템 사용, 제작 횟수 등.
  • 소셜: 파티(결성·해체 시각, 참여 계정), 문파(8주차 기준 문파원), 거래(누가 누구와 언제 무엇을 얼마나).
  • 결제 이력: 이탈과 결제의 상관이 높다는 선행 연구에 따라 제공했습니다.
  • 학습 1만 명, 평가 4만 명. 라벨 비율을 같게 맞췄고, 표준화·익명화했습니다.
결과
  • 531팀 참가, 93팀 최종 제출, 12팀 2차 심사. 평가는 4개 라벨의 정밀도·재현율 8개 값의 조화 평균(F1)입니다.
  • 대부분 F1 0.70~0.75였습니다(출제팀 예상 0.6~0.7).
  • 도구: Python 57팀, R 28팀. 알고리즘 27종 중 랜덤 포레스트(51), XGBoost(45), LightGBM(26), 로지스틱 회귀(15)가 많았습니다. 최고 팀과 최저 팀이 모두 랜덤 포레스트를 써서, 알고리즘보다는 가장 많이 선택된 모델이었다고 봐야 한다고 했습니다.
  • 한 수상팀은 AWS에 대규모 자원을 투입해 많은 모델과 하이퍼파라미터 조합을 몇 시간 만에 시험했습니다.
우수 접근법과 아쉬움
  • 주별 데이터를 계정당 한 행으로 펼치고 합계·평균·분산·최댓값·최솟값과 기울기·이동평균 추세를 만들었습니다. 요인 분석, 비선형 변환, k-means·계층·t-SNE 군집화도 썼습니다.
  • "Level 0" 팀은 유저를 작업장 의심 집단, 일반 고객, 튜토리얼만 하고 떠난 더미 집단으로 나눠 도메인 지식을 활용했습니다.
  • 소셜 네트워크 분석을 시도한 팀이 없었던 점이 아쉽다고 했습니다. 온라인 게임 이탈은 게임 안 사회 관계와 관련이 깊기 때문입니다.
  • 모델 해석 결과를 이탈 원인으로 단정하면 안 된다고 경고했습니다. 모델의 분류 기준과 이탈 원인은 다릅니다.
우리 프로젝트에 주는 시사점 · 실제 대회 참가팀이 "작업장 의심 집단"을 따로 분류했다는 것은 작업장이 실제 로그에서 눈에 띄는 집단이라는 방증입니다. 출제자가 아쉬워한 "소셜 네트워크 분석"을 우리가 2단계에서 정면으로 다루면 차별점이 됩니다.

OSRS Wiki Real-time Prices API

제공
Old School RuneScape Wiki × RuneLite
원문
oldschool.runescape.wiki
언어
영어 → 번역
엔드포인트 (기본 주소 https://prices.runescape.wiki/api/v2/osrs)
경로내용파라미터
/latest아이템별 최신 고가·저가와 거래 시각(Unix). 한 번도 거래되지 않은 아이템은 빠집니다.id (선택)
/mapping아이템 목록: 이름, ID, 설명, 회원 여부, 하이·로우 알케미 값, 거래소 구매 한도, 가치, 아이콘없음
/5m5분 평균 고가·저가와 거래량timestamp (선택)
/1h1시간 평균 고가·저가와 거래량timestamp (선택)
/timeseries한 아이템의 가격 이력id, lookback (6h·24h·7d·30d·6m·1y) 필수
이용 규칙
  • 명시적인 호출 제한은 없지만, API 안정을 위협하면(초당 여러 건의 큰 요청을 계속 보내는 경우 등) 제한할 수 있습니다.
  • 아이템마다 id로 반복 호출하지 말고, id 없이 한 번에 전체를 받으라고 합니다. 자원을 약 100배 덜 씁니다.
  • 설명이 담긴 User-Agent가 유일한 필수 조건입니다. python-requests, Python-urllib, Apache-HttpClient, RestSharp, Java, curl 기본값은 미리 차단돼 있습니다.
  • 가격은 32비트 정수 범위를 넘을 수 있어 64비트 이상 타입을 써야 합니다.
  • 실시간 파이프라인을 만들면 위키 디스코드의 #api-discussion 채널에 알려 변경 공지를 받으라고 권합니다.
  • 위키 콘텐츠 라이선스는 CC BY-NC-SA 3.0입니다. API 데이터에 대한 별도 조건은 적혀 있지 않습니다.
